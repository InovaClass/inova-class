## Project Conventions

### Scope

This is **inova.class**, a gamified classroom management platform (an alternative to Classcraft), started from [next-boilerplate](https://github.com/diasjoaovitor/next-boilerplate). Choices outside the toolchain and the UI layer (database, ORM, auth, data fetching, state management, hosting) are made per task and recorded in the issue that introduces them. The one opinion on the UI side is **shadcn/ui** as the component library, with its theme and Tailwind's default palette kept as they come (see Styling & UI).

### Package manager

- Use **pnpm** only (not npm/yarn).
- Versions are pinned exact (no `^`/`~`) only for `dependencies` and `devDependencies` in `package.json`, no exceptions there. Install new deps with `pnpm add -E <pkg>` (or `pnpm add -D -E <pkg>` for dev deps) — never hand-edit version strings.
- `-E` only takes effect when no version is given. `pnpm add -E <pkg>@<version>` (or `@latest`) and packages already in `package.json` still get a `^`. In those cases, remove the carets right after (`sed -i -E 's/"\^([0-9])/"\1/' package.json`) and run `pnpm install`.
- The exact-version rule does not apply to MCP servers (`.mcp.json`) or `package.json` scripts, which may use `@latest` (e.g. `pnpm dlx shadcn@latest`, `pnpm dlx @playwright/mcp@latest`). They must still run through pnpm, never `npx`.
- Node version is pinned in `.nvmrc` (`lts/krypton`) for local use and in `engines.node` (`24.x`) in `package.json` for hosts that ignore `.nvmrc` (e.g. Vercel). Keep both on the same major.
- On Vercel, set `ENABLE_EXPERIMENTAL_COREPACK=1` (Production and Preview) so the build uses the exact pnpm version from `packageManager`; without it Vercel picks pnpm from the lockfile version.
- `minimumReleaseAge` in `pnpm-workspace.yaml` (7 days, in minutes) keeps pnpm from resolving a version published less than a week ago.
- `@/*` resolves to `src/*` (`tsconfig.json`).

### Project structure

- `src/app` holds frontend-exclusive content only — there's no top-level `src/components` or `src/helpers`, that shared code lives under `src/app` instead.
- Anything that isn't frontend-exclusive (e.g. `src/tests`, and any future non-frontend folder) lives directly under `src`, as a sibling of `app`, not nested inside it.
- Server code is layered, and imports only flow down: `app` → `entry` → `dtos`/`models` → `repositories` → `infra`, with `constants` as a leaf every layer may import (it imports none of them) and `src/types` next to `dtos`/`models`. `no-restricted-imports` in `eslint.config.mjs` enforces the direction per folder.
  - `src/entry/` adapts Server Components and Server Actions to the models: `form-action.ts` (the wrapper every form's Server Action goes through, see Forms; not a Server Action itself) and `session.ts` (`getSession()`, cached per request with `React.cache`, and the `requireSession()`/`requireRole()` guards). The name refers to where requests enter the server code, not to a bundle entry point.
  - `src/models/<domain>/` holds the business rules of one domain: `model.ts` declares each async function as its own `const` and exports `<domain>Model`, an object that only lists them, at the end of the file. It's the only file that calls `infra` services (`errors.ts` may import its error classes); `schema.ts` holds its Zod schemas, each followed by its input type (`export type SignUpInput = z.input<typeof signUpSchema>`), and imports nothing server-only, so client forms import it directly. Form state types (`FormState<SignUpInput>`) stay in the route's `action.ts`, since `schema.ts` doesn't import `entry`; any other file (`errors.ts`, `constants.ts`, `utils.ts`) is added when the domain needs it. A model validates its own input (`schema.parse(input)`) and throws `infra/errors.ts` errors, never framework or library ones. Functions that need the request take its `headers` (and any route) as arguments instead of reading `next/headers`, so integration tests can call them.
  - `src/infra/` holds the technical pieces: `auth.ts` (the Better Auth config), `database/`, `email/`, and `errors.ts` (`AppError` and its subclasses, with a user-facing `message` and `action`).
  - Mark a module that must never reach the client with `import 'server-only'` (aliased to an empty module in `vitest.config.mts`), as in `src/entry/session.ts`. `src/infra/auth.ts` stays without it: the Better Auth CLI loads that file outside Next.js and can't resolve the import.
  - `src/constants/<topic>.ts` holds values shared across layers (e.g. `USER_ROLES`, the password length bounds that both the Zod schemas and Better Auth use).
  - `src/repositories/<domain>-repo.ts` exports `<domain>Repo`, the queries on our own Drizzle tables, once a model needs more than one or two, in the same shape as a model: each query is its own `const` and the object that lists them comes at the end of the file. It holds no business rules and only models call it.
  - Not created yet, add each with its first use: `src/dtos/<domain>-dto.ts` for what a page or API may expose of an entity, decided per viewer (#6). `src/types/` only for types shared across layers.
- `actions.ts`/`action.ts` with `'use server'` is only for mutations called from the client. A function a Server Component calls to read data is not a Server Action: name its file `data.ts`.
- Routes are grouped under `src/app/(pages)` (a route group, so it doesn't affect the URL).
- Shared frontend code lives in `src/app/components`, React hooks in `src/app/hooks` and other helpers in `src/app/helpers` (create them when the first one is needed). The `lib` alias in `components.json` points to `src/app/lib`, which doesn't exist: if the shadcn CLI ever creates something there, keep it in `lib` or move it to `helpers` case by case.
- Imports of the same folder or of a direct subfolder are relative (`./file`, `./folder/file`). Every other import goes through the `@/` alias (e.g. `@/app/components/ui/shadcn/button`), never `../`, which ESLint rejects.
- There are no `index.ts` barrels: import each module directly from its file. Barrels cause circular imports, give two import paths for the same module and make Vite/Vitest load every re-exported module.
- `src/app/components` groups components by role: `ui/` for visual building blocks (shadcn ones under `ui/shadcn/`, the 8bitcn ports under `ui/8bit/`, our own under `ui/custom/`), `blocks/` for composed pieces reused across pages, grouped by domain (e.g. `blocks/post/`; a block that belongs to no domain stays directly in `blocks/`), and `providers/` for context providers without UI of their own.
- A layout stays in the `layout.tsx` of its route or route group (e.g. `(pages)/(teacher)/layout.tsx`), with the parts only it uses in a private `_components/` folder next to it. Parts used by a single page also live in a `_components/` folder next to it. Parts shared only by the pages of one route group live in the group's own `_components/` (e.g. `(pages)/(auth)/_components/`) and are imported only by pages inside that group. A helper that isn't a component or a form's action (e.g. `(pages)/(auth)/google-notice.ts`) sits at the root of the route or group it serves, not in `_components/` nor in `src/app/helpers`, which is for helpers shared across the app.
- `favicon.ico` stays directly in `src/app/`, not nested in a route group.
- React Compiler is enabled (`reactCompiler: true` in `next.config.ts`, `babel-plugin-react-compiler` devDependency).

### Classes

- A class (`classes` table, `src/models/class/`) belongs to one teacher. In code it's `schoolClass`, since `class` is a reserved word and `characterClass` is the game concept (#18). Its routes live under `/professor/turmas`.
- Every `classModel` function takes the `teacherId` and filters by owner and `archivedAt`, so the role check of the page or action isn't what keeps a class private. A class of another teacher, an archived class and a malformed id get the same answer: `findOwned` returns `undefined`, which a page turns into `notFound()`, and `update`/`archive` throw `NotFoundError`.
- Archiving sets `archivedAt` and keeps the data; there's no way to restore a class yet.
- An action that changes a class calls `revalidatePath('/professor', 'layout')`, so the Back button doesn't bring a stale page from the client cache.
- Every class has a join code (`joinCode`, `joinCodeEnabled`), with the format in `src/constants/class.ts`. A teacher regenerates it (after a confirmation) or turns it off on the class page. `enrollmentModel.join` (`src/models/enrollment/`, table `enrollments`) enrolls a student immediately: an unknown code, a disabled one and that of an archived class get the same field error, and joining twice keeps one enrollment. `join` gives the student only the name of the class back. `/aluno` lists the student's classes (`enrollmentModel.listClasses`, name and description only, without an archived class or an ended enrollment); the cards have no link until the student class page exists (#22). Game stats (#18) go on the enrollment, not on the account.
- A teacher invites students at `/professor/turmas/[id]/alunos/novo`, pasting one `name, email` per line (`studentModel.invite`, `src/models/student/`). A new email gets an account without a `credential` row, a generated username, the enrollment and an invite email; a pending student (role `student` with no row in `accounts`) gets the enrollment and a new link; an active student gets the enrollment and a notice; a teacher account gets nothing. The answer is the same in every case, so the form doesn't reveal which emails have an account. `users.createdById` records the teacher.
- An invite is a row in `verifications` (`student-invite:<token>`, 7 days, only the latest one of a student works), not Better Auth's reset token, which lasts 1 hour and doesn't verify the email. `/convite` shows the username and `studentModel.acceptInvite` sets the password, verifies the email, records `termsAcceptedAt` and signs the student in. `authenticationModel.requestPasswordReset` sends a pending student a new invite, so the password never skips the terms acceptance.
- The class page lists the students (`enrollmentModel.listRoster`), with the email of a pending student, whom the teacher invited, and the username of the others: one who joined by code never gave the email to the teacher. A list that also marks who is pending reveals to a teacher which invited emails have an account, unlike the invite form's answer; that's accepted (#60 reviews it).
- Removing a student (`enrollmentModel.remove`) sets `endedAt` on the enrollment and keeps the account, so a query for the students of a class must filter by it. A student comes back through the join code or a new invite, which reactivate the same enrollment (`reactivateEndedEnrollment`), so never `onConflictDoNothing` on `enrollments`. To keep them out, the teacher regenerates or disables the code.
- The routes of the teacher area have no `loading.tsx` of their own: `(pages)/loading.tsx` covers the first load, and a link inside the area keeps the current page until the next one is ready.

### Database & local services

- Postgres with **Drizzle ORM** and the `pg` (node-postgres) driver, so the same code runs against the local container and Neon in preview/production. `drizzle-orm` and `drizzle-kit` are on the `1.0.0` release candidate (installed from the `@rc` tag, as the current Drizzle docs do): check the types in `node_modules/drizzle-orm` before reaching for a v0 API (e.g. `drizzle()` no longer takes `schema`, and the config has no `casing`).
- Infrastructure lives in `src/infra`: `compose.yml` declares the local services (Docker Compose, not `docker-compose.yml`): `database` (Postgres) and `mail` (Mailpit, SMTP on `1025`, UI and API on `8025`). `scripts/` holds the startup helpers, `database/` holds `client.ts`, `schema.ts` and the generated `migrations/`, `auth.ts` the Better Auth config and `email/` the mailer and templates. A piece stays a single file until it needs a second one; `scripts/` is a folder because its files run on their own. `drizzle.config.ts` stays at the root, where `drizzle-kit` looks for it.
- Tables are declared with `snakeCase.table(...)` from `drizzle-orm/pg-core`, so camelCase keys map to snake_case columns.
- Schema changes go through `pnpm migrations:generate --name <name>`, and the generated folder is committed. Don't edit a migration that was already applied; generate a new one.
- `pnpm dev` is the startup script: `services:up` → `services:wait:database` → `migrations:up` → `next dev`. The compose services have no healthcheck because readiness is the wait script's job. Playwright's `webServer` (and so the pre-push hook and CI) goes through the same `pnpm dev`, so CI needs no service container.
- Local settings live in the committed `.env.development` (only local-only values: the containers' credentials and URLs, plus a `BETTER_AUTH_SECRET` that no hosted environment uses; never a hosted secret). There is no `.env`/`.env.example`. The compose services read it through `env_file`, so the `POSTGRES_*` values are declared once there; `DATABASE_URL` repeats them literally (`process.loadEnvFile` doesn't expand variables), so keep both in sync. `drizzle.config.ts` and the wait script load `.env.development` only when `DATABASE_URL` isn't already set, so hosted environments keep their injected value. `drizzle.config.ts` prefers `DATABASE_URL_UNPOOLED` (Neon's direct connection) over the pooled `DATABASE_URL`.
- The git-ignored `.env.local` (created by `vercel link`) holds the `VERCEL_OIDC_TOKEN` and, optionally, your own `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` for Google sign-in. Don't `vercel env pull` the Neon variables into it: `.env.local` takes precedence over `.env.development`, so `next dev` would hit Neon. The Neon integration is connected to Production and Preview only, not Development.

### Forms

- Forms use **React Hook Form** (`react-hook-form`, with `@hookform/resolvers`) and uncontrolled inputs for client-side validation, with the model's **Zod** schema, and call **Server Actions** with the typed values. They need JavaScript. Stay on `react-hook-form` v7: its docs only declare React Compiler support for v8, still in beta, so the forms' e2e tests are what covers the compiler (Vitest runs without it).
- A form lives in the route's `_components/`: `action.ts` (`'use server'`) and `<name>-form.tsx` (`'use client'`). The schema comes from `src/models/<domain>/schema.ts`. It only declares rules and messages for Zod, so it has no unit test of its own: the forms' e2e tests cover what the user sees.
- `action.ts` receives the typed input, wraps the model call in `formAction(input, async (values) => ...)` (`src/entry/form-action.ts`) and returns `formSuccess(message)` or calls `redirect()`. The wrapper turns whatever the model throws into the `FormState` the form renders:
  - a `ZodError` becomes `errors` (the first message per field, a nested field under its dotted path, e.g. `links.0.url`);
  - an `AppError` becomes `message` + `action` for the whole form. A business rule that belongs to one field is thrown as a `ZodError` with that `path`;
  - anything else is logged and shown as a generic message, so the user never sees an error boundary for a failed submit;
  - `redirect()`/`notFound()` are rethrown (`unstable_rethrow`).

  It also gives every result a unique `id`, so a repeated identical error still updates the UI.

- The client form calls `useFormAction({ schema, defaultValues, action })` (`src/app/hooks/use-form-action.ts`) and renders `<form {...formProps}>`, a `<FormField label=... {...field('name')} />` per field (`name` is typed by the schema's fields), `<FormMessage state={state} announcement={announcement} />` and `<SubmitButton pending={pending}>`. `FormCard` (adapted from 8bitcn's `login-form` block), `FormField`, `FormCheckbox` (takes the hook's `control`), `FieldFrame`, `FormMessage` and `SubmitButton` live in `src/app/components/ui/custom/`. `FieldFrame` holds the label, hint and error of a field and hands the ids and ARIA attributes to its child, so a control other than the text input of `FormField` goes inside it. Pages build notices (e.g. from `?error=`) with `formError(...)`/`formSuccess(...)` and pass them as `initialState`.
- `GoogleSignInForm` has no fields, so it stays on `useActionState` with the same `formAction`, `FormMessage` and `SubmitButton`.
- How it behaves, so don't "simplify" it away:
  - The `<form>` keeps `method="post"`, so a click before hydration never puts a password in the URL. `onSubmit` validates on the client and calls the action inside `startTransition`, the only way `redirect()` reaches the `RedirectBoundary`; nothing resets the form.
  - Field errors live only in React Hook Form. With `mode: 'onTouched'` a field shows its error once it was left or the form was submitted, and revalidates on every change after that. Server field errors arrive through `setError`, and each one hides once its field is edited.
  - React Hook Form validates one field at a time, so a field another one depends on is declared with `field('password', { revalidates: 'passwordConfirmation' })`. It only revalidates a field already visited or invalid; `deps` would reveal an error on a field not visited yet.
  - `SubmitButton` prevents the default of `mousedown`, so the focus stays on the field: the blur would reveal its error and move the button under the pointer, losing the click. Don't replace it with a check of the blur's `relatedTarget`: Safari doesn't focus a button on click. `FormCard` does the same for the links inside it.
  - After a failed submit (client or server) React Hook Form moves the focus to the first invalid field, before the commit that adds its `aria-invalid` and error description. That loss is accepted, since `FormMessage` reads out the first field error (`announcement`). The announcement also covers a field that already has the focus, where moving the focus announces nothing. A client-side rejection clears the previous answer of the Server Action. A visible form message (success, an `AppError`, or one rendered with the page such as an expired link) takes the focus. `FormMessage` is a live region that stays mounted (`sr-only` while empty); `SubmitButton` uses `focusableWhenDisabled` so focus survives the pending state; that sets `aria-disabled` instead of `disabled`, so it styles the `aria-disabled:` state itself, shows the 8bit `Spinner` while pending and announces the pending state in its own live region, since not every screen reader voices `aria-disabled` on the focused button. `FormMessage` turns the live region `sr-only` whenever there's no visible message, not with `empty:sr-only`, since the announcement alone would add a gap to the form.
  - `FieldFrame` builds its ids with `useId`, so two forms on a page never share an `id`. In e2e tests, check a field error with `toHaveAccessibleDescription` on the field rather than `getByText`, which also matches the announcement.

### Auth & email

- **Better Auth** (`src/infra/auth.ts`) with `drizzleAdapter` from `@better-auth/drizzle-adapter/relations-v2` (the plain export targets Drizzle v0), `usePlural` and `generateId: 'uuid'`. Its tables live in `src/infra/database/schema.ts`, hand-written in the `snakeCase.table` style: when a Better Auth plugin or option adds fields, run `pnpm dlx auth@latest generate --config src/infra/auth.ts --output <scratch file>`, port the diff by hand and generate a migration. Never point `--output` at `schema.ts`.
- `role` (`teacher` | `student`) is an `additionalField` with `input: false` and `defaultValue: 'teacher'`: Better Auth rejects it from any request body, even server-side calls, so the role of a new account comes only from the server flow that creates it. The model wraps every sign-up in `withSignUpRole(role, ...)` (an `AsyncLocalStorage` in `src/infra/auth.ts`) and `databaseHooks.user.create.before` applies it; for Google, a `before` hook on `/sign-in/social` copies it into the OAuth state with `addOAuthServerContext`, which the callback request reads back with `getOAuthState()`. A request straight to `/api/auth/sign-up/email` has no role and gets a `403`, since it would skip the terms acceptance. Never read the role from `additionalData` or the request body.
- The terms live at `/termos` and `/privacidade` (`(pages)/(legal)/`, with the controller's name, the contact email and the update date in `legal-info.ts`). Every sign-up records `termsAcceptedAt` (`input: false`) together with the role in `databaseHooks.user.create.before`, so a new flow that calls `withSignUpRole` must collect the acceptance first. The email forms require the `acceptedTerms` checkbox and the model rejects a sign-up without it; on Google the sign-up page shows `GoogleTermsNotice` next to the button. Accounts older than #7 keep `termsAcceptedAt` empty.
- `/cadastro` is the role choice; `/cadastro/professor` and `/cadastro/aluno` are the sign-up pages. Every account has a valid email, verified before its first sign-in, students included; students also have a `username` (Better Auth `username` plugin, rules in `src/constants/user.ts`, stored in lowercase). `/entrar` serves both roles with a single "E-mail ou usuário" field: a value with `@` signs in by email, any other by username, and every credential failure shows the same copy.
- `baseURL` is dynamic (`allowedHosts`), so each Preview URL works without `BETTER_AUTH_URL`. Only this project's hosts are listed; never add `*.vercel.app`, which would trust any Vercel deployment.
- Google sign-in (`socialProviders.google`) is enabled only when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set; pages check `isGoogleSignInEnabled` and hide "Continuar com o Google" without them, so tests and CI never need the credentials. `disableImplicitSignUp` keeps Google from creating an account on `/entrar`: only a sign-up page passes a `signUpRole` (which turns on `requestSignUp`), so the user always picks the role. `mapProfileToUser` drops the Google picture, so a Google account keeps only what the sign-up form would collect (name and email). Account linking is Better Auth's default for every role (Google links only when both sides verified the same email). The callback's `?error=` lands on the page with `?origem=google` and is shown by the Google form itself (`googleNoticeFrom` in `(pages)/(auth)/google-notice.ts`), so a new attempt replaces it; on each sign-up page the Google form is a child of the sign-up form, which hides it after an email sign-up, since Google can't link to the still unverified account. On Vercel, `oAuthProxy` sends Previews through the production callback (`OAUTH_PROXY_SECRET`, the same in Production and Preview), since Google doesn't accept wildcard redirect URIs; locally Google uses its own `localhost` redirect URI, so the plugin is off and the proxy secret never leaves Vercel. The Google Cloud setup is in `README.md` (#44).
- `src/models/authentication/` wraps `auth.api.*` (sign-up, sign-in, password reset): the auth pages' actions call it with `headers: await headers()` (the dynamic `baseURL` and rate limiting need the request host/IP), and `nextCookies()` stays the last plugin so those actions can set cookies. Its `errors.ts` maps the Better Auth error codes we expect to `UnauthorizedError`/`ValidationError` copy; a code without copy stays an unexpected error. Pages read the session with `getSession()` from `src/entry/session.ts`. `src/app/api/auth/[...all]/route.ts` serves the links sent by email (verification, password reset).
- Teachers land on `/professor` and students on `/aluno` (`DASHBOARD_PATHS` in `src/constants/user.ts`), and `/` redirects to the sign-in page or to the dashboard of the user's role. A page of a role area calls `requireRole(role)` from `src/entry/session.ts`, and so does its layout, which also needs the user: a layout doesn't re-run on client navigation nor stop the page below it from rendering, so the check in the layout alone isn't enough. `requireRole` sends a signed-out user to `/entrar` and a user of another role to their own dashboard. There is no `proxy.ts`: the role lives in the database and the proxy also runs on prefetches, so it could only read the cookie. A Server Action of a role area makes the same check, since it can be called without going through the page.
- Emails are sent with `nodemailer` over SMTP (`src/infra/email/mailer.ts`): Resend's SMTP (`smtp.resend.com`, the API key as password, sending as `nao-responda@` the integration's `RESEND_EMAIL_DOMAIN`) when `RESEND_API_KEY` is set, else `SMTP_URL` (Mailpit). The transporter is created per send, so importing the module never needs the variables (`next build`, the Better Auth CLI). Auth emails are scheduled with `after()` so their timing doesn't reveal whether an account exists. `scheduleEmails` does the same for a list, one at a time, and a failed address doesn't stop the others. Links in these emails take their host from `appBaseURL(headers)` (`src/infra/auth.ts`), which applies `allowedHosts`, never directly from the `Host` header.
- The Resend integration (domain `inovaclass.diasjoaovitor.com.br`, region `sa-east-1`) is connected to Production and Preview only (`vercel integration add resend/resend-email -e production -e preview --no-env-pull`): pulling `RESEND_API_KEY` into `.env.local` would make local runs send real email.
- Tests read emails from Mailpit through `orchestrator.waitForLinkSentTo(email)` (`src/tests/orchestrator.ts`).

### Linting & formatting

- ESLint uses native flat config (`eslint.config.mjs`), extending the `core-web-vitals`/`typescript` configs from `eslint-config-next`, plus `eslint-plugin-unicorn`, `eslint-plugin-simple-import-sort`, `eslint-plugin-tailwindcss`, `eslint-plugin-promise`, `eslint-plugin-prefer-arrow-functions`, `eslint-config-prettier`, and `@eslint/json`/`@eslint/markdown` for JSON/Markdown files. Markdown files use the `gfm` language with `frontmatter: 'yaml'`, so the frontmatter of issue templates (or any Markdown content) isn't parsed as Markdown. `eslint-plugin-tailwindcss` rule docs are in `node_modules/eslint-plugin-tailwindcss/docs/rules/` — check there before overriding a Tailwind lint rule.
- `eslint-plugin-unicorn@74` declares a peer of `eslint >=10.4`, but the project stays on ESLint 9 (`9.39.5`). The peer is unmet (`pnpm peers check` reports it, and depending on the pnpm version install warns `Issues with peer dependencies found`), but `pnpm eslint:check` passes. Don't bump one without validating the other.
- `next lint` no longer exists (removed in Next.js 16). Use `pnpm eslint:check` / `pnpm eslint:fix` and `pnpm prettier:check` / `pnpm prettier:fix`.
- `pnpm type-check` runs `next typegen` first: globals such as `LayoutProps` are generated into `.next/types`, so a clean checkout (CI, fresh clone) fails `tsc --noEmit` without it.
- The `review-copy` skill (`.claude/skills/review-copy/`) reviews the text in the code (naming, comments, test descriptions, UI copy, docs); use it on a diff before opening a pull request.
- Prettier style: single quotes, no semicolons, no trailing commas (`.prettierrc`).
- Base indentation/whitespace rules (2 spaces, LF, trim trailing whitespace, final newline) are enforced editor-side via `.editorconfig`.

### Code comments

- Comments only record **why** a decision was made, ideally with a reference (docs link, issue number, upstream bug). Never write comments that explain what the code does or how it works.
- Default to no comment. Add one only for a non-obvious choice that someone might "fix" by mistake.
- Write comments in English.

### Git hooks (husky)

- `pre-commit`: runs `lint-staged` (`lint-staged.config.js`) — prettier + eslint + `vitest related --project unit --passWithNoTests` scoped per staged file type, invoked directly via `pnpm exec` rather than through `package.json` scripts.
- `commit-msg`: auto-prepends the emoji prefix from the Commit Rules below based on the leading word (e.g. `feat: ...` → `✨ feat: ...`), then runs `commitlint` (`commitlint-config-emoji-convention`). You can type the plain word and let the hook add the emoji.
- `pre-push`: runs `pnpm type-check`, `pnpm test:integration` and `pnpm test:e2e` (full Playwright suite).

### Testing

- Unit tests: **Vitest** (`vitest.config.mts`, project `unit`), `jsdom` environment, native Vite `resolve.tsconfigPaths` (no `vite-tsconfig-paths` plugin needed). Picks up `src/**/*.test.{ts,tsx}` outside `src/tests`, next to the code they test. Component tests use `@testing-library/react` / `@testing-library/dom`. `vitest.setup.ts` (`setupFiles`) runs Testing Library's `cleanup` after every test, so test files don't repeat `afterEach(cleanup)`.
- Integration tests: Vitest project `integration` (`node` environment, files run one at a time), in `src/tests/integration/`, mirroring the layer they test (e.g. `models/authentication.test.ts`). They call models against the local Postgres and Mailpit, so `pnpm test:integration` starts the services and migrates first. `src/tests/integration/setup.ts` loads `.env.development` and replaces `after()` from `next/server`, which only works inside a Next.js request, with a plain call. Shared test helpers (`newUser()`, `newStudent()`, `newClass()`, `newEmail()`, `newUsername()`, `newPassword()`, reading Mailpit) live in `src/tests/orchestrator.ts`, used by integration and e2e tests alike. Use unique data per test instead of clearing the database: test data comes from `@faker-js/faker` (`fakerPT_BR`) through the orchestrator, except emails and usernames, which carry a UUID so they never repeat, and literal values that are the point of the test (e.g. an invalid email).
- E2E tests: **Playwright** (`playwright.config.ts`), tests live in `src/tests/e2e`, single `chromium` project, `webServer` auto-starts `pnpm dev` against `http://localhost:3000`. Failure artifacts go to `test-results/` (git- and ESLint-ignored). Assertions wait up to 15s (`expect.timeout`) and a test up to 60s (`timeout`), since `pnpm dev` compiles each route on its first request; don't lower them to the defaults of 5s and 30s. Local runs use 3 workers (`workers`), since more compile too many routes at once on a cold `.next`. There are no global retries: a known flaky test gets `test.describe.configure({ retries })` in its own `describe`, with a comment linking the issue that tracks it.
- Only test logic we wrote (filtering, lookups, mappings, transforms, a model's rules and error mapping). Don't test library or framework behavior (e.g. a component that only passes props or HTML through, a Zod schema's `trim`/`min`/`max` and the messages we hand it, `Link` routing), and drop a test whose main cost is a mock needed only to render. Prefer a unit test; add an e2e test only for what a unit test can't cover.
- Older issues may ask for tests that break the rule above. Skip them without asking, and list them as dropped in the closing comment.
- Scripts: `pnpm test` (unit, run once) / `pnpm test:watch` (unit, watch mode) / `pnpm test:integration` (services + migrations + integration) / `pnpm test:e2e` (e2e) / `pnpm test:e2e:ui` (e2e, Playwright UI mode). `lint-staged` runs `vitest related --project unit`, so commits never need the services.
- CI (`.github/workflows/ci.yml`, triggered on `pull_request`) runs, in order: `commitlint` over the PR's commit range, `pnpm type-check`, `pnpm eslint:check`, `pnpm prettier:check`, `pnpm test`, `pnpm test:integration`, then installs Chromium (`pnpm exec playwright install --with-deps chromium`) and runs `pnpm test:e2e`.

### Styling & UI

- Tailwind CSS v4 (`@tailwindcss/postcss` only — no `autoprefixer`/`postcss`, v4 uses Lightning CSS internally). Global styles live in `src/app/styles/globals.css`, which also imports `tw-animate-css` and the shadcn base stylesheet (`shadcn/tailwind.css`).
- Dark mode follows the system preference: the `dark:` variant is bound to `prefers-color-scheme` (`@custom-variant dark (@media (prefers-color-scheme: dark))`) and the dark tokens are redefined on `:root` inside the same media query, instead of shadcn's `.dark` class. A project that needs a manual theme toggle switches both to a class (e.g. with `next-themes`).
- Visual identity is retro 8-bit pixel art, full retro: every text (headings, body, labels, inputs) uses `Press Start 2P` (`next/font/google`, which covers the Latin-1 glyphs Portuguese needs), mapped to `--font-sans`, `--font-mono` and `--font-heading`, and `html` applies the `retro` utility. Don't mix in a modern font (e.g. Geist) for body text; use `text-xs`/`text-sm` and `leading-relaxed` for long copy instead, as the 8bitcn blocks do. `globals.css` adds the `retro` (pixel font), `pixelated` (`image-rendering`) and `pixel-border` (notched frame drawn by `::before`/`::after` outside the element, colored by `--pixel-border`) utilities.
- Game tokens live in `globals.css` next to the shadcn ones, for both themes, as Tailwind palette colors (500 in light, 400 in dark): `--hp`, `--xp`, `--coin` and one per character class (`--class-warrior`, `--class-mage`, `--class-healer`), exposed as `bg-hp`, `text-coin`, `bg-class-mage`, ... Use them for game values instead of picking a palette color per screen.
- `src/app/components/ui/8bit/` holds components ported from [8bitcn](https://github.com/theorcdev/8bitcn-ui) (MIT) as wrappers over our `base-nova` shadcn components: `alert-dialog`, `button`, `card`, `checkbox`, `input`, `label` and `textarea` so far, plus `spinner` and `empty`, standalone upstream with no shadcn counterpart. 8bitcn is built on Radix and `@/lib/utils`, so never install it with `pnpm shadcn:add @8bitcn/...`: port each component by hand onto Base UI (`render` instead of `asChild`) and the `cn` package, only when a feature needs it, and keep the credit comment at the top of the file. Add the underlying shadcn component first if it's missing, and port only the parts that change: the rest is imported from `ui/shadcn/` (e.g. `CardTitle`). The 8bit `font` variant defaults to `retro`, as upstream. Because the pixel frame covers the area a `ring-*` would draw on, 8bit components show focus with an `outline` offset past the frame. Plain links get their focus `outline` from `globals.css`, since shadcn's base `outline-ring/50` is too faint against the background.
- Prefer [8bitcn blocks](https://www.8bitcn.com/docs/blocks) (auth forms, menus, leaderboards, quest logs, dialogues, 404 pages, ...): before building a page or section, check whether a block covers it and start from it instead of composing from scratch. Read its source from the registry (`https://8bitcn.com/r/<block>.json`, the `content` of each file), never install it with the CLI, and port it like an 8bit component: onto our `ui/8bit/` and `ui/shadcn/` components (port any missing 8bit component first), Base UI, `cn`, arrow functions and pt-BR copy, with a credit comment linking the block's docs page. Keep its structure, sizes and spacing, and change only what our conventions or the feature require (Server Actions, accessibility, our tokens). A ported block lives in `blocks/<domain>/` when pages of different route groups use it, else in the `_components/` of the route or route group that uses it (e.g. `login-form` became `ui/custom/form-card.tsx`, a generic piece every form uses).
- Don't retint the default colors: keep the shadcn tokens in `globals.css` (`neutral` base color) and Tailwind's palette as they come, and pick an existing palette color instead of a custom shade (e.g. `teal-500`, not a tinted `oklch(...)`). Prefer the shadcn tokens (`bg-background`, `text-muted-foreground`, `border-border`, ...) for surfaces and text, so both themes stay consistent. Where CSS variables can't be read (a canvas, `ImageResponse`), copy the palette value and name it in a comment.
- **shadcn/ui** (`components.json`, style `base-nova`, base color `neutral`, icon library `lucide`) is the component library: reach for a shadcn component before writing one from scratch. They live in `src/app/components/ui/shadcn/`. Add components with `pnpm shadcn:add <name>` (wraps `pnpm dlx shadcn@latest add`) — aliases and target paths are in `components.json`. When the CLI asks to overwrite a component that's already there (e.g. `button.tsx`, a dependency of `alert-dialog`), answer no: without a terminal, pipe it with `yes n | pnpm shadcn:add <name>`. Components from other shadcn registries are added the same way (`pnpm shadcn:add @<registry>/<name> --path src/app/components/ui/<registry>`), after declaring the registry in `components.json`; pin any dependency the CLI installs with `^`.
- Links that need to look like a `Button` (e.g. external CTAs) must stay plain `<a>`/`Link` elements styled with the exported `buttonVariants(...)` helper (`linkButtonVariants(...)` from `ui/8bit/button` for the 8-bit look), not `Button` itself — Base UI's `Button` enforces button semantics (`role="button"`, keyboard handling) and its own docs say not to render links through it.
- Supporting libs: `@base-ui/react` (headless primitives), `class-variance-authority` for variant styling, `cn` for the `cn()` class-merging helper (imported directly from the `cn` package, as the shadcn components do; there is no `lib/utils.ts` re-export, see https://ui.shadcn.com/docs/changelog/2026-09-cn), `lucide-react` for icons. Before wiring up a Base UI primitive, check its docs in `node_modules/@base-ui/react/docs/react/` (`components/`, `utils/`, `handbook/`) for its semantics/keyboard behavior — component APIs there may differ from other headless UI kits.

## Development Workflow

The end-to-end flow (planning, issues, branches, commits, pull requests and closing) is described in [`docs/development-workflow.md`](./docs/development-workflow.md). Follow it for any issue.

## Branch Rules

Work for an issue is committed on a new branch, never directly on `main`. Branch names follow `<scope>/<title>#<issue>`, or `<scope>(<target>)/<title>#<issue>` when the work is very specific:

- `<scope>` is one of the semantic prefixes from the Commit Rules below, without the emoji (`feat`, `fix`, `docs`, `chore`, ...).
- `(<target>)` is optional: the page, component or other specific area the work touches (e.g. `home`, `card`).
- `<title>` is a short, lowercase, hyphen-separated summary in English.
- `#<issue>` is the number of the associated issue.

Examples: `feat/home-page#3`, `fix(card)/focus-ring#7`. Parentheses and `#` are special characters in shells, so quote the branch name in commands (e.g. `git switch -c 'fix(card)/focus-ring#7'`).

## Issue Rules

Before closing an issue, tick every completed checklist item (`- [x]`) in its body, e.g. with `gh issue edit <number> --body-file <file>`. Don't close an issue that still has unchecked items unless they were dropped or moved, and say so in the closing comment.

## Documentation Rules

`AGENTS.md` and `README.md` record only project conventions: what to do, where things live and how to handle a given case. Answers to the user's one-off questions (e.g. "why don't we use X?") stay in the conversation and are not written into them. Keep a "why" only when it prevents a likely mistaken "fix". If a change touches a convention, update both files in the same branch.

## Task Rules

Never start working on a task on your own, even when asked to move on to the next one or in auto/agentic mode. First present a summary of the plan (the issue, branch name, steps, files touched and any open decisions) and wait for explicit approval before creating the branch, installing dependencies or editing code. Read-only investigation (issues, docs, code) needs no approval.

## Commit Rules

Never run `git commit` on your own, even in auto/agentic mode. Only propose a commit message when the user asks for one, and create the commit only after explicit approval of that message.

Commit messages must be in English and follow this format:

- Use the following semantic prefixes: `🎉 init, ✨ feat, 🐛 fix, 📚 docs, 💎 style, 📦 refactor, 🚀 perf, 🚨 test, 🛠 build, ⚙️ ci, ♻️ chore, 🗑 revert`
- The message must be in the imperative mood and in lowercase.
- Write the commit body.
- Reference an associated issue by number, if it exists, using the format `Issue: #<number>`.

Example:

```text
✨ feat: add product page

Add the new product page for the product listing with the following features:
- Create a new product
- Update a product
- Delete a product

Issue: #1
```
