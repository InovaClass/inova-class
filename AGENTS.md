## Project Conventions

### Scope

This is **inova.class**, a gamified classroom management platform (an alternative to Classcraft), started from [next-boilerplate](https://github.com/diasjoaovitor/next-boilerplate). Choices outside the toolchain and the UI layer (database, ORM, auth, data fetching, state management, hosting) are made per task and recorded in the issue that introduces them. The one opinion on the UI side is **shadcn/ui** as the component library, with its theme and Tailwind's default palette kept as they come (see Styling & UI).

### Package manager

- Use **pnpm** only (not npm/yarn).
- Versions are pinned exact (no `^`/`~`) only for `dependencies` and `devDependencies` in `package.json`, no exceptions there. Install new deps with `pnpm add -E <pkg>` (or `pnpm add -D -E <pkg>` for dev deps) — never hand-edit version strings.
- `-E` only takes effect when no version is given. `pnpm add -E <pkg>@<version>` (or `@latest`) and packages already in `package.json` still get a `^`. In those cases, remove the carets right after (`sed -i -E 's/"\^([0-9])/"\1/' package.json`) and run `pnpm install`.
- The exact-version rule does not apply to MCP servers (`.mcp.json`) or `package.json` scripts, which may use `@latest` (e.g. `pnpm dlx shadcn@latest`, `pnpm dlx @playwright/mcp@latest`). They must still run through pnpm, never `npx`.
- Node version is pinned in `.nvmrc` (`lts/krypton`) for local use and in `engines.node` (`24.x`) in `package.json` for hosts that ignore `.nvmrc` (e.g. Vercel). Keep both on the same major.
- On Vercel, set `ENABLE_EXPERIMENTAL_COREPACK=1` (Production and Preview) so the build uses the exact pnpm version from `packageManager`; without it Vercel picks pnpm from the lockfile version.
- `minimumReleaseAge` in `pnpm-workspace.yaml` (7 days, in minutes) keeps pnpm from resolving a version published less than a week ago.
- `@/*` resolves to `src/*` (`tsconfig.json`).

### Project structure

- `src/app` holds frontend-exclusive content only — there's no top-level `src/components` or `src/helpers`, that shared code lives under `src/app` instead.
- Anything that isn't frontend-exclusive (e.g. `src/tests`, and any future non-frontend folder) lives directly under `src`, as a sibling of `app`, not nested inside it.
- Server code is layered, and imports only flow down: `app` → `entry` → `dtos`/`models` → `repositories` → `infra`, with `constants` as a leaf every layer may import (it imports none of them) and `src/types` next to `dtos`/`models`. `no-restricted-imports` in `eslint.config.mjs` enforces the direction per folder.
  - `src/entry/` adapts Server Components and Server Actions to the models: `form-action.ts` (the wrapper every form's Server Action goes through, see Forms; not a Server Action itself) and `session.ts` (`getSession()`, cached per request with `React.cache`, and the `requireSession()`/`requireRole()` guards). The name refers to where requests enter the server code, not to a bundle entry point.
  - `src/models/<domain>/` holds the business rules of one domain: `model.ts` declares each async function as its own `const` and exports `<domain>Model`, an object that only lists them, at the end of the file. It's the only file that calls `infra` services (`errors.ts` may import its error classes); `schema.ts` holds its Zod schemas, each followed by its input type (`export type SignUpInput = z.input<typeof signUpSchema>`), and imports nothing server-only, so client forms import it directly. Form state types (`FormState<SignUpInput>`) stay in the route's `action.ts`, since `schema.ts` doesn't import `entry`; any other file (`errors.ts`, `constants.ts`, `utils.ts`) is added when the domain needs it. A model validates its own input (`schema.parse(input)`) and throws `infra/errors.ts` errors, never framework or library ones. Functions that need the request take its `headers` (and any route) as arguments instead of reading `next/headers`, so integration tests can call them.
  - `src/infra/` holds the technical pieces: `auth.ts` (the Better Auth config), `database/`, `email/`, and `errors.ts` (`AppError` and its subclasses, with a user-facing `message` and `action`).
  - Mark a module that must never reach the client with `import 'server-only'` (aliased to an empty module in `vitest.config.mts`), as in `src/entry/session.ts`. `src/infra/auth.ts` stays without it: the Better Auth CLI loads that file outside Next.js and can't resolve the import.
  - `src/constants/<topic>.ts` holds only values used by more than one domain or by a layer below the models (e.g. `USER_ROLES`, the password length bounds that both the Zod schemas and Better Auth use). A value that belongs to one domain lives in its `src/models/<domain>/constants.ts`, even when a page, a test or a related domain imports it (e.g. `JOIN_CODE_LENGTH` in `models/class/`).
  - `src/repositories/<domain>-repo.ts` exports `<domain>Repo`, the queries on our own Drizzle tables, once a model needs more than one or two, in the same shape as a model: each query is its own `const` and the object that lists them comes at the end of the file. It holds no business rules and only models call it.
  - Not created yet, add each with its first use: `src/dtos/<domain>-dto.ts` for what a page or API may expose of an entity, decided per viewer (#6). `src/types/` only for types shared across layers.
- `actions.ts`/`action.ts` with `'use server'` is only for mutations called from the client. A function a Server Component calls to read data is not a Server Action: name its file `data.ts`.
- Routes are grouped under `src/app/(pages)` (a route group, so it doesn't affect the URL).
- Shared frontend code lives in `src/app/components`, React hooks in `src/app/hooks` and other helpers in `src/app/helpers` (create them when the first one is needed). The `lib` alias in `components.json` points to `src/app/lib`, which doesn't exist: if the shadcn CLI ever creates something there, keep it in `lib` or move it to `helpers` case by case.
- Imports of the same folder or of a direct subfolder are relative (`./file`, `./folder/file`). Every other import goes through the `@/` alias (e.g. `@/app/components/ui/shadcn/button`), never `../`, which ESLint rejects.
- There are no `index.ts` barrels: import each module directly from its file. Barrels cause circular imports, give two import paths for the same module and make Vite/Vitest load every re-exported module.
- `src/app/components` groups components by role: `ui/` for visual building blocks (shadcn ones under `ui/shadcn/`, the 8bitcn ports under `ui/8bit/`, our own under `ui/custom/`), `blocks/` for composed pieces reused across pages, grouped by domain (e.g. `blocks/post/`; a block that belongs to no domain stays directly in `blocks/`), and `providers/` for context providers without UI of their own.
- A layout stays in the `layout.tsx` of its route or route group (e.g. `(pages)/(teacher)/layout.tsx`), with the parts only it uses in a private `_components/` folder next to it. Parts used by a single page also live in a `_components/` folder next to it. Parts shared only by the pages of one route group live in the group's own `_components/` (e.g. `(pages)/(auth)/_components/`) and are imported only by pages inside that group. A helper that isn't a component or a form's action (e.g. `(pages)/(auth)/google-notice.ts`) sits at the root of the route or group it serves, not in `_components/` nor in `src/app/helpers`, which is for helpers shared across the app.
- `favicon.ico` stays directly in `src/app/`, not nested in a route group.
- The root layout (`layout.tsx`), `not-found.tsx` and `global-error.tsx` also stay directly in `src/app/`: Next.js only serves the root `not-found.tsx` for an unknown URL, and with the root layout inside a route group it falls back to its own English page. `not-found.tsx` also covers every `notFound()`, and `(pages)/error.tsx` an error while rendering a page. The three render `StatusScreen` (`ui/custom/`, ported from 8bitcn's `not-found1` block, with our fallen warrior instead of its ogre), and the error screens show fixed copy, since a Server Component's `error.message` is generic in production. `global-error.tsx` replaces the root layout, so it imports `globals.css` and the font itself.
- React Compiler is enabled (`reactCompiler: true` in `next.config.ts`, `babel-plugin-react-compiler` devDependency).
- Avoid `'use client'` as far as possible. It isn't a strict rule, since some components only work on the client (state, effects, event handlers), but keep the directive on the smallest piece that needs it and leave the rest as Server Components. A Base UI primitive already carries its own directive, so a wrapper that only passes it serializable props doesn't need one.

### Classes

- A class (`classes` table, `src/models/class/`) belongs to one teacher. In code it's `schoolClass`, since `class` is a reserved word and `characterClass` is the game concept (#18). Its routes live under `/professor/turmas`.
- Every `classModel` function takes the `teacherId` and filters by owner and `archivedAt`, so the role check of the page or action isn't what keeps a class private. A class of another teacher, an archived class and a malformed id get the same answer: `findOwned` returns `undefined`, which a page turns into `notFound()`, and `update`/`archive` throw `NotFoundError`, as `restore` does for a class that isn't archived.
- Archiving sets `archivedAt` and keeps the data. `/professor/turmas/arquivadas` lists the archived classes, and `classModel.restore` clears `archivedAt` without a confirmation, since nothing is lost: the class comes back with its students and its join code, which works again unless the teacher had turned it off.
- An action that changes a class calls `revalidatePath('/professor', 'layout')`, so the Back button doesn't bring a stale page from the client cache.
- Every class has a join code (`joinCode`, `joinCodeEnabled`), with the format in `src/models/class/constants.ts`. A teacher regenerates it (after a confirmation) or turns it off on the class page. `enrollmentModel.join` (`src/models/enrollment/`, table `enrollments`) enrolls a student immediately: an unknown code, a disabled one and that of an archived class get the same field error, and joining twice keeps one enrollment. `join` gives the student only the id of the class back, and the form redirects to the class page. It allows 10 attempts with a wrong code per student every 15 minutes (`src/models/enrollment/constants.ts`, table `join_attempts`), and past that even a right code is rejected, with a message saying when to try again. The limit is per student, not per IP, since a classroom shares one; a code of the wrong length isn't counted, since it never reaches the database. `/aluno` lists the student's classes (`enrollmentModel.listClasses`, name and description only, without an archived class or an ended enrollment), each linking to `/aluno/turmas/[id]`. Game stats and the character go on the enrollment, not on the account.
- A teacher invites students at `/professor/turmas/[id]/alunos/novo`, pasting one `name, email` per line (`studentModel.invite`, `src/models/student/`). A new email gets an account without a `credential` row, a generated username, the enrollment and an invite email; a pending student (role `student` with no row in `accounts`) gets the enrollment and a new link; an active student gets the enrollment and a notice; a teacher account gets nothing. The answer is the same in every case, so the form doesn't reveal which emails have an account. `users.createdById` records the teacher.
- An invite is a row in `verifications` (`student-invite:<token>`, 7 days, only the latest one of a student works), not Better Auth's reset token, which lasts 1 hour and doesn't verify the email. `/convite` shows the username and `studentModel.acceptInvite` sets the password, verifies the email, records `termsAcceptedAt` and signs the student in. `authenticationModel.requestPasswordReset` and `authenticationModel.resendVerificationEmail` send a pending student a new invite, so neither a password nor a verification link (which signs the user in) skips the terms acceptance.
- The class page lists the students (`enrollmentModel.listRoster`), with the email of a pending student, whom the teacher invited, and the username of the others: one who joined by code never gave the email to the teacher. A list that also marks who is pending reveals to a teacher which invited emails have an account, unlike the invite form's answer; that's accepted (#60 reviews it).
- Removing a student (`enrollmentModel.remove`) sets `endedAt` on the enrollment and keeps the account, so a query for the students of a class must filter by it. A student comes back through the join code or a new invite, which reactivate the same enrollment (`reactivateEndedEnrollment`), so never `onConflictDoNothing` on `enrollments`. To keep them out, the teacher regenerates or disables the code.
- The routes of the teacher area have no `loading.tsx` of their own: `(pages)/loading.tsx` covers the first load, and a link inside the area keeps the current page until the next one is ready.

### Game ledger

- XP, HP and coins live on the enrollment (`enrollments.xp`, `hp`, `coins`), as a cache of `ledger_entries`. Only `ledgerModel` (`src/models/ledger/`) changes them (`record`, `recordBatch`, `reverseBatch`, `reverseEntry`): in one transaction it locks the enrollment rows (`for('update')` in `ledgerRepo`), inserts the entries and their derived entries and writes the new balances, so concurrent entries never drift from the history. Never write the balances anywhere else, and never update or delete an entry: a correction is a new entry (#16). Check constraints on `enrollments` reject a negative XP or coin balance and an HP outside `0..HP_MAX`.
- An entry stores the deltas actually applied: HP is clamped to `0..HP_MAX` (`src/constants/game.ts`) and a coin penalty takes only what the student has, so reversing an entry restores the balances exactly. A spend that must not go through without the coins (a purchase, a power) passes `requireCoins: true` and gets `ValidationError`.
- XP only goes down in a `reversal` entry, which the schema enforces. The level isn't stored: `levelOf(xp)` (`src/models/ledger/level.ts`) derives it from a curve fixed in code (level n takes `50·n·(n−1)` XP). Each level crossed upward adds a `level_bonus` entry of `LEVEL_BONUS_COINS`, with `parentEntryId` pointing to the entry that crossed it; losing a level takes no bonus back, since the reversal of the original entry also reverses its bonuses.
- `sourceId` points to the behavior, consequence, power, reward or owned item behind the entry, without a foreign key since the target table depends on `type`. `LEDGER_ENTRY_TYPES` lists every type the game uses, including the ones of later issues.
- A batch is a set of entries that share `batchId`, applied by `ledgerModel.recordBatch` in one transaction that locks the enrollments in the order of their ids: it reaches every student or none. `ledgerModel.reverseBatch` adds a `reversal` entry per entry of the batch, derived ones included, each pointing to it through `reversedEntryId`, which is unique, so an entry is never reversed twice. A reversal has no `batchId` and goes through the same limits as any entry, so coins already spent can't be taken back.
- `ledgerModel.reverseEntry` does the same for one entry and its derived ones. Only a `behavior` or a `quest_reward` entry of a student still in the class can be reversed from the history: a purchase, a power and an HP restore have flows of their own. Once one student of a batch was reversed, `reverseBatch` rejects the batch, and the other students are reversed from the history. `reverseBatch` only takes a batch of `behavior` entries: a completed objective goes back per student, since the reversal also returns the submission.
- `/professor/turmas/[id]/historico` lists the entries of the class (`?aluno=<id>` for one student, `?pagina=N`, `HISTORY_PAGE_SIZE` per page), each with its level bonuses and reversal nested. A student who left the class stays listed.

### Behaviors

- A behavior (`behaviors` table, `src/models/behavior/`) belongs to one class and holds the XP, HP and coins an award of it applies. Every `behaviorModel` function takes the `teacherId` and the `classId` and filters by owner, by an active class and by `removedAt`, like `classModel`: another teacher's behavior, a removed one and a malformed id all get `undefined` or `NotFoundError`.
- A class starts with `DEFAULT_BEHAVIORS` (`src/models/behavior/constants.ts`), inserted in the same transaction as the class (`classRepo.insert`). Classes created before #14 have none.
- XP is never negative (a check constraint too), and a behavior either gives points or takes them: `kindOf` (`src/models/behavior/kind.ts`) classifies it as `positive` or `negative`, and the schema rejects a behavior with every value at zero or with values of both signs. The error goes on the field to fix (the first value against the sign of the first non-zero one, or `xp` when all are zero), so each value field revalidates the other two. The kind isn't stored. The values are text inputs, not `type="number"`, which reports a value it can't parse as blank, and blank counts as zero.
- Removing a behavior sets `removedAt` and keeps the row, since `ledger_entries.sourceId` points to it. Editing it changes only the next entries: an entry stores its own deltas.
- The teacher manages them at `/professor/turmas/[id]/comportamentos`. `BehaviorForm` lives in `(pages)/(teacher)/_components/`, shared by the pages of the teacher area, and `ConfirmActionDialog` in `ui/custom/`, since the student's shop uses it too. Signed values are shown with the hyphen-minus (`-5 HP`): Press Start 2P has no `−` (U+2212), which would fall back to Arial.
- The teacher awards them on the class page: `behaviorModel.award` takes the selected students and either applies the behavior to all of them or to none, and `behaviorModel.undoAward` reverses the whole batch. A pending student can receive a behavior, since the enrollment already exists. The "Desfazer" toast lasts 15 seconds; there is no time limit on the server.

### Consequences

- A consequence (`consequences` table, `src/models/consequence/`) belongs to one class and is only a name. `consequenceModel` filters by owner, active class and `removedAt`, like `behaviorModel`, and removing one sets `removedAt`, since `ledger_entries.sourceId` points to it. A class starts with `DEFAULT_CONSEQUENCES`, inserted in the same transaction as the class; classes created before #17 have none.
- A student is fallen when `hp` is 0. It isn't stored, so a reversal or an award that gives HP takes the student out of it. The UI says "Sem HP", which doesn't depend on the student's gender.
- `/professor/turmas/[id]/alunos/[student-id]/sorteio` is the draw. `consequenceModel.draw` picks on the server and `ledgerModel.restoreFallen` adds an `hp_restore` entry of `+HP_MAX`, with the consequence as `sourceId`. It checks that the HP is 0 under the lock of the enrollment, so two concurrent draws never both go through. Without a consequence the draw is refused and the HP stays at 0. An `hp_restore` entry can't be reversed.

### Powers

- A power (`powers` table, `src/models/power/`) belongs to one class and one character class, with a name, an optional description, a coin cost and a minimum level. `powerModel` filters by owner, active class and `removedAt`, like `behaviorModel`. `characterClass` isn't listed in the database, as on `enrollments`: the schema validates it against `CHARACTER_CLASSES`.
- A class starts with `DEFAULT_POWERS` (`src/models/power/constants.ts`, a list per character class), inserted in the same transaction as the class; classes created before #19 have none.
- Disabling one (`disabledAt`, "Desativar"/"Reativar", without a confirmation) hides it from the students and keeps it listed for the teacher. Removing one sets `removedAt`, since `ledger_entries.sourceId` points to it.
- The teacher manages them at `/professor/turmas/[id]/poderes`, grouped by character class, with `PowerForm` in `(pages)/(teacher)/_components/`. The toggle keeps the focus, so its success is only announced, not shown with `FormMessage`, which would take it.
- `/aluno/turmas/[id]` lists the enabled powers of the student's character class once the character is chosen (`powerModel.listForStudent`), each `unlocked` when `levelOf(xp)` reaches its minimum level.

### Power requests

- Using a power changes the rules of the class, so the teacher approves each use. A request (`power_requests` table, `src/models/power-request/`) belongs to one enrollment and one power and copies its `cost`, so editing the power doesn't change what a pending request holds. `status` is `pending`, `approved`, `refused` or `canceled` (`POWER_REQUEST_STATUSES`, `src/constants/game.ts`), and a request leaves `pending` only once.
- A pending request reserves its cost without touching the balances: `availableCoins` (`balance.ts`) takes the cost of every pending request out of `enrollments.coins`. `powerRequestModel.request` checks it, the minimum level, the character class and that the power isn't already pending under the lock of the enrollment (the one `ledgerRepo` takes), so two requests never reserve the same coins; a unique partial index keeps one pending request per power. A reward purchase checks `availableCoins` too.
- A coin penalty doesn't respect the reservations and takes only what the student has, so `availableCoins` never goes below zero, and an approval whose cost the coins no longer cover is refused with `studentLacksCoins` and stays pending, for the teacher to refuse.
- `powerRequestModel.approve` calls `ledgerModel.spendOnPower`, which adds a `power` entry (`-cost`, the power as `sourceId`) and settles the request in the same transaction (`ledgerRepo.record`'s `afterWrite`), so the entry and the decision never come apart. A `power` entry can't be reversed. Refusing and canceling only change `status`, since no coin left the enrollment.
- The student requests and cancels on `/aluno/turmas/[id]`, where "Pedidos pendentes" lists every pending request, including one for a power the teacher disabled or removed afterwards: it still reserves its cost until someone decides it. The teacher decides at `/professor/turmas/[id]/pedidos`, linked from the class page with the count of pending requests. Approving goes through `ConfirmActionDialog` (with `confirmVariant="default"`, since nothing is lost), because a `power` entry can't be reversed; refusing doesn't, since it only releases the reservation. Removing a student refuses their pending requests in the same transaction (`enrollmentRepo.end`), so one who comes back finds no coins reserved.

### Rewards

- A reward (`rewards` table, `src/models/reward/`) belongs to one class, with a name, an optional description, a coin price and an optional stock (empty for no limit, a blank field in the form). `rewardModel` filters by owner, active class and `removedAt`, like `behaviorModel`, and removing one sets `removedAt`, since `ledger_entries.sourceId` and the orders point to it. A class starts with `DEFAULT_REWARDS`, inserted in the same transaction as the class; classes created before #21 have none.
- Unlike a power, a purchase pays at once: `rewardOrderModel.purchase` (`src/models/reward-order/`) calls `ledgerModel.spendOnReward`, which, under the lock of the enrollment, locks the reward, checks the stock and `availableCoins` (`checkPurchase`), takes a unit, adds a `reward_purchase` entry (`-price`, the reward as `sourceId`) and inserts the order (`reward_orders`, `pending`), all in one transaction. The order copies the `price`, so editing the reward never changes what a cancellation refunds.
- The teacher decides at `/professor/turmas/[id]/entregas`, linked from the class page with the count of pending orders. "Entregar" only changes `status` to `delivered`. "Cancelar" (after a confirmation, whose dismiss button reads "Voltar") calls `ledgerModel.refundReward`, which adds a `reward_refund` entry (`+price`) instead of a reversal, sets `canceled` with `refundEntryId` and puts the unit back in stock in the same transaction. Neither entry can be reversed from the history, and an order leaves `pending` only once.
- Removing a student leaves their pending orders as they are: the coins already left, so the teacher still delivers or refunds them, and the list marks the student with "Saiu da turma".
- The student buys on `/aluno/turmas/[id]` ("Loja", without needing a character), where "Meus pedidos" lists the latest `STUDENT_ORDERS_LIMIT` orders, the pending ones first. The student can't cancel an order, so "Comprar" goes through `ConfirmActionDialog` (with `confirmVariant="default"`).

### Cosmetic items

- The items are global, not per class: `ITEM_CATALOG` (`src/models/item/constants.ts`, next to the sprite manifest) gives each item of `AVATAR_MANIFEST.items` a pt-BR name, a slot (`head` or `face`), a coin price, a minimum level and, optionally, the one character class that may wear it. A new item is imported with `pnpm sprites:import` first, and a unit test keeps the catalog and the manifest in step.
- The inventory belongs to the account (`owned_items`, unique per student and item), so an item bought in one class is used in every other without a second purchase. `purchaseEntryId` goes to null instead of taking the item along, since the item outlives the class it was bought in.
- `itemModel.purchase` (`src/models/item/`) pays at once and needs no approval, since cosmetics don't change the class: `ledgerModel.spendOnItem` adds an `item_purchase` entry (`-price`, with the `owned_items` row as `sourceId`, since an item id isn't a UUID) and, under the lock of the enrollment, checks the rules of `checkItemPurchase` (`rules.ts`): the shop of the class is open, the item isn't owned yet, it fits the character class, the level of this enrollment reaches it and `availableCoins` covers it. Two classes lock different enrollments, so the unique constraint is what stops a second purchase of the same item, and the losing one rolls back. An `item_purchase` entry can't be reversed or refunded.
- A purchase needs the character, so `/aluno/turmas/[id]` shows "Itens" only once it's chosen, each row with a still preview of the character wearing the item. "Comprar" goes through `ConfirmActionDialog` (with `confirmVariant="default"`); "Equipar"/"Desequipar" is one `ActionButton`, so the focus stays on it when the label changes, and its success is only announced.
- `itemModel.equip`/`unequip` write `equippedItems` of the enrollment, one item per slot (`equipItem` replaces the item of the same slot). Equipping checks the inventory, the character class and the level of the class where the item is used, so an item bought at a high level elsewhere may stay locked here. It only writes while the character class is the one it checked against, as `characterModel.updateAppearance` does. An item dropped from the manifest is ignored when the column is read.
- The teacher closes or opens the shop of a class on `/professor/turmas/[id]/recompensas` (`classes.itemShopEnabled`, on by default, "Fechar loja de itens"/"Abrir loja de itens" without a confirmation). A closed shop stops purchases in that class only; the student still lists the items they own and puts them on or takes them off.
- A purchase sends the `ledger` event, as any entry does; equipping sends none and shows on the next refresh.

### Missions

- A mission (`missions` table, `src/models/mission/`) belongs to one class and holds a sequence of objectives (`objectives`), each with a story, an optional due date, the XP and coins it gives and a late penalty in coins and HP, never XP, since XP only goes down in a `reversal` entry. `missionModel` filters by owner, active class and `removedAt`, like `behaviorModel`, and so do the objectives through their mission. Removing a mission or an objective sets `removedAt`, since the `quest_reward` entries and the submissions point to it.
- Only the objectives have an order: missions are listed drafts first and then by creation, and the map column comes with its catalog (#97). The issues of the milestone describe the old Firestore modeling; follow this one.
- `objectives.position` isn't unique: a swap would break the index halfway, and a removed objective keeps its own. Creating, moving and removing an objective run under the lock of the mission row (`missionRepo.withLocked`), a new one goes after the last active one, and a move (`moveItem`, `order.ts`) rewrites the positions of the active ones from 0, so no gap is left.
- `dueOn` is a `date`, since the teacher picks a day: a submission is late when its date in `America/Sao_Paulo` is after it. A late penalty needs a due date, and the reward needs XP or coins (the schema and check constraints enforce both). `formatDueOn` (`src/app/helpers/objective-values.ts`) reads it as UTC, so it never shows the day before.
- A mission starts as a draft, hidden from the students. `missionModel.publish` sets `publishedAt` once, without a confirmation, only with an objective, and a published mission never goes back to draft nor loses its last objective.
- The teacher manages them at `/professor/turmas/[id]/missoes` and the objectives of each at `/professor/turmas/[id]/missoes/[mission-id]`, with `MissionForm` and `ObjectiveForm` in `(pages)/(teacher)/_components/`. "Subir"/"Descer" are `ActionButton`s, left out at either end of the list; a reorder drops the focus, so the list moves it back to a button of the moved row and only announces the new position.

### Mission submissions

- A submission (`objective_submissions` table, `src/models/objective-submission/`) belongs to one enrollment and one objective, with the student's text, an optional `http`/`https` link, `status` (`pending`, `approved` or `returned`, `OBJECTIVE_SUBMISSION_STATUSES` in `src/constants/game.ts`) and the teacher's comment on a return. Each send is a new row, so a returned one stays next to the one that replaced it, and a unique partial index keeps one `pending` or `approved` submission per objective and enrollment.
- An objective is available to a student once the previous active objective of the mission has any submission of theirs, a returned one included (`isAvailable`, `rules.ts`), so a slow review never blocks the student. `objectiveSubmissionModel.submit` checks it under the lock of the enrollment, the one `ledgerRepo` takes, and only for a published mission.
- `objectiveSubmissionModel.approve` calls `ledgerModel.payQuest`, which adds a `quest_reward` entry (the objective as `sourceId`) and settles the submission in the same transaction (`afterWrite`). The reward comes from the objective as it is at approval, as a behavior's does. A submission sent after `dueOn` (`isLate`, its date in `America/Sao_Paulo`) also gets a `quest_penalty` entry, derived from the reward like a level bonus (`parentEntryId`), so it can't be recorded on its own, goes through the usual limits and is reversed together with the reward.
- Returning a submission needs a comment and only changes `status`. Reversing a `quest_reward` entry from the history reverses its penalty and level bonuses and returns the submission in the same transaction (`objectiveSubmissionRepo.returnPaid`), without a comment, so the student can send it again.
- The teacher completes an objective of a published mission for the selected students at `/professor/turmas/[id]/missoes/[mission-id]/objetivos/[objective-id]/concluir` (`objectiveSubmissionModel.complete`): one batch of `quest_reward` entries (`ledgerModel.payQuestBatch`) and an `approved` row without text per student, never a late penalty, since it's an activity done in class that the teacher marks when they can. It lists only the active students without a pending or approved submission, pending students included, and the batch reaches all of them or none. `FormCheckboxGroup` (`ui/custom/`) renders the selection.
- The teacher approves or returns at `/professor/turmas/[id]/missoes/entregas` ("Entregas de missões", linked from the class page with the count of pending ones), oldest first, with "Atrasada" on a late one. "Aprovar" has no confirmation, since the reward can be reversed; "Devolver" opens a dialog with the comment. A submission of an objective or mission removed afterwards still waits for a decision. A student who left the class has their pending submissions hidden and can't be approved, and finds them pending again on coming back.
- The student follows the published missions at `/aluno/turmas/[id]/missoes` and each one at `/aluno/turmas/[id]/missoes/[mission-id]` (`objectiveSubmissionModel.listMissionsForStudent`/`findMissionForStudent`, `undefined` for a draft, a removed mission, one of another class and a student who left, as `findOfStudent` does). Each active objective gets a state from its latest submission (`objectiveStatesOf`, `rules.ts`): `pending`, `approved`, or else `locked` while it isn't available (a returned one too) and `available` or `returned` after. A locked objective gives only its name, so the story stays a surprise. The current objective is the first `available` or `returned` one, else the first `pending` (`currentObjectiveIndex`); without one the mission is done. A removed objective leaves the student's view, while its pending submission still waits for the teacher.
- An `available` or `returned` objective shows the form to send it (`SubmissionForm`, named by the objective's heading, since every objective's form has the same fields), a returned one with the teacher's comment and the text and link sent before. The form leaves once it's sent, so the list's `FormMessage` shows the success and takes the focus, until the teacher takes an objective out of `pending`, which makes it stale. The mission page shows `StudentStats` too, so an approval while the student reads it animates; it and `MissionSummaryList` live in `(student)/_components/`, since several pages of the group use them. The class page lists the missions with a current objective under "Missões", each linking to it (`#objetivo-<id>`, from `mission-links.ts` at the root of `(student)`, with the item taking the focus Next.js gives the target), and "Ver todas as missões" leads to the finished ones too.

### Student class view and ranking

- `/aluno/turmas/[id]` opens with "Seu progresso" (`StudentStats`): the avatar animated in `idle`, the level, the XP of the level, the HP and the coins, from `enrollmentModel.findOfStudent`. Before the character is chosen it shows the stats without the avatar.
- `/aluno/turmas/[id]/historico` lists the student's own entries (`ledgerModel.listStudentHistory`), with the same pages, level bonuses and reversals as the teacher's history, but without the author or "Reverter". A student who left the class gets `notFound()`, as on the class page. Both histories take their titles and values from `src/app/helpers/ledger-entry.ts` and their page links from `PageNav` (`blocks/page-nav.tsx`).
- The ranking (`rank`, `src/models/enrollment/ranking.ts`) orders the active students of a class by XP, then by name in pt-BR, and tied students share a position (1, 1, 3). Pending students are in it, since they can already receive behaviors.
- The teacher always sees it at `/professor/turmas/[id]/ranking` (`enrollmentModel.listRanking`), with the username or a pending student's email, and shows or hides it for the students there (`classes.rankingVisible`, off by default, "Mostrar aos alunos"/"Ocultar dos alunos" without a confirmation). Students see it on the class page only while it's on (`enrollmentModel.listRankingForStudent`, which returns `undefined` otherwise), with each classmate's name, avatar, level and XP: no id, contact, HP or coins, so the rows are keyed by their index. `Leaderboard` (`blocks/class/`, ported from 8bitcn's block) renders both, with each avatar `still` and "Você" on the student's own row.

### Class events

- A screen of a class learns that something changed through Server-Sent Events, not a WebSocket: the events only go from the server to the screens, and `upgradeWebSocket()` from `@vercel/functions` needs the Vercel runtime, which `next dev` (and so the e2e tests) lacks. `GET /api/turmas/[id]/eventos` (`src/app/api/turmas/[id]/eventos/route.ts`) streams them, with a heartbeat every 25 seconds.
- An event is only `{ type }` (`CLASS_EVENT_TYPES`, `src/models/class-event/constants.ts`): `ledger`, `power-request`, `reward-order` or `mission`. It carries no data, so the screen fetches again through the reads that already check who sees what. `classEventModel.publish` (`src/models/class-event/`) sends it on the channel `class:<id>` after the transaction commits, and `ledgerModel`, `powerRequestModel`, `rewardOrderModel` and `objectiveSubmissionModel` call it after every change, so a new flow that changes them gets its event for free. An approval or a purchase also sends `ledger`, since the coins changed.
- Publishing never fails the change: without `REDIS_URL` it does nothing, and a Redis that doesn't answer in 1 second is logged and skipped (`src/infra/realtime.ts`, with the offline queue off, so a command never waits for a reconnection). Every screen keeps working without the events.
- `classEventModel.listen` lets in the teacher who owns the active class and a student with an active enrollment, and gives `undefined` to anyone else, as `classModel.findOwned` does: the route answers `401` without a session, `404` for a class the user can't see and `503` when Redis is down or `REDIS_URL` isn't set. Access is checked when the stream opens, so a student removed afterwards keeps getting the signals, which carry no data, until the stream reconnects.
- Each instance keeps one publisher and one subscriber connection, shared by every stream. A script outside Next.js (the seeds, the integration tests) calls `closeRealtime()` at the end, or its process never exits.
- `useClassEvents(classId, onEvent)` (`src/app/hooks/use-class-events.ts`) subscribes a client component. The browser reconnects by itself after a network error, but gives up on any other response, so the hook opens a new stream with a delay doubling from 1 to 30 seconds. After a reconnection it calls `onEvent('resync')`, since the events sent in between are lost.
- A page of a class renders `ClassEventsRefresh` (`blocks/class/`) with the event types of the values it shows, which calls `router.refresh()` on them and on `resync`: the page reads again through its own models, and the client state of what stays on the page (the selected students, a draw result) is kept. A refresh can remove the row of the focused control or of an open dialog (another student bought the last unit, the student canceled the request), so when the focus drops to the body it moves to the page's `h1` (`restoreLostFocus`, `src/app/helpers/`). The class pages of the teacher and of the student listen to all four, the student's mission page to `mission` and `ledger` and the list of missions to `mission`, the draw page, both histories and the teacher's ranking to `ledger`, "Pedidos" to `power-request`, "Entregas" to `reward-order` and "Entregas de missões" and the completion of an objective to `mission`. Reversing a `quest_reward` entry also sends `mission`. A new screen of a class that shows these values renders it too. Other changes (a new reward, a disabled power, the ranking shown to the students) send no event and show on the next navigation.
- Hosted environments have no Redis yet: Upstash through the Vercel Marketplace, which sets `REDIS_URL`, comes with the production deploy (#28).

### Gameplay animations

- Animations use **Motion** (`motion/react`). Each animated piece wraps itself in `<MotionConfig reducedMotion="user">`, so under `prefers-reduced-motion` the movement is dropped and only the fades stay; what can't be reduced to a fade (the draw roulette) checks `useReducedMotion()` and skips straight to the end.
- An event carries no data (see Class events), so an animation never comes from the event: `useStatChanges` (`src/app/hooks/`) compares the XP, HP and coins a page renders with the ones it rendered before (`statChangeOf`, `src/app/helpers/stat-change.ts`) and keeps one entry per change. The same comparison covers a change that arrives through `router.refresh()` and one the user's own action brings, such as a purchase. Its state is a single object updated from the current value, since a render that a transition restarts would otherwise record the change twice. The first render records nothing, so opening a page doesn't animate.
- `StatsAvatar` (`blocks/class/`) renders the avatar with the change: `hurt` when the HP goes down, `cast` when the XP or the HP goes up (`avatarAnimationFor`), and the "+XP", "-HP" and coin numbers floating over it (`FloatingDeltas`, hidden from assistive technology, since the values on the page already change). The roster shows it `still` between changes. On the student's own screen (`celebrate`) a level-up shows `LevelUpOverlay`, which neither takes the focus nor blocks the page, and is announced in a live region; on the roster it's one more floating number.
- The draw page shows a roulette (`rouletteNames`, next to the page) with the names of the consequences after the server has drawn, and only then reveals the result, which takes the focus.
- The pages that only list values (histories, ranking) don't animate.

### Sound effects

- The effects are chiptune sounds synthesized with [jsfxr](https://github.com/chr15m/jsfxr) (a devDependency) from the fixed parameters in `src/infra/scripts/generate-sounds.ts`, not from its presets, which roll new values on every run. `pnpm sounds:generate` writes them to `public/sounds/` with a hash of the content in the file name (served as `immutable`, like the sprites) and regenerates `src/app/helpers/sound-manifest.ts`. Both are committed; change a sound in the script and run it again. They're ours, released as CC0 and credited at `/creditos`.
- A sound follows the same changes as the animations: `StatsAvatar` plays `soundFor(change)` (`stat-change.ts`, one sound per change: `level-up`, then `hurt`, then `power-up` for XP or HP gained, then `coins`; spending coins plays nothing), and the draw result plays `draw`. `useGameSound(effect, trigger)` (`src/app/hooks/`) plays it whenever `trigger` changes.
- `playSound` (`src/app/helpers/game-sound.ts`) plays each effect at most once per `REPEAT_WINDOW_IN_MS`, so a behavior awarded to the whole roster sounds once. Before the person interacts with the page the browser keeps audio off, and a sound from then is dropped instead of queued. A sound that fails to load or play is only logged.
- Sounds are on by default. `SoundToggle` (`blocks/`, in `AppHeader`, so both layouts have it) mutes them per browser, in `localStorage` (`sound-preference.ts`, read with `useSoundMuted`), and keeps the choice in memory when the storage is blocked. It's a toggle button (`aria-pressed`) with a fixed label, repeated in `title` for pointer users, and a speaker drawn on an 8 px grid, since lucide's smooth strokes clash with the pixel font.

### Avatar

- A student's character is pixel art from the [Universal LPC Spritesheet Character Generator](https://github.com/LiberatedPixelCup/Universal-LPC-Spritesheet-Character-Generator), pinned to a commit in `src/infra/scripts/import-lpc-sprites.ts`, which also lists the parts we use: the body types, skins, hair styles and colors, the outfit of each character class with its colors, and the items.
- `pnpm sprites:import` downloads them and writes one sheet per layer to `public/sprites/lpc/`: the front-facing row of `idle`, `slash` (our `attack`), `spellcast` (`cast`) and `hurt`, with the upstream frame cycles baked in, so every animation steps at the same 8 fps. The colors are swapped with the upstream palettes at import time, not in the browser, and a layer blank from the front is dropped. It also regenerates `src/models/avatar/manifest.ts` (the options, the layers of each part and the credits). Both are committed; never edit a sheet or the manifest by hand, change the script and run it again.
- Each sheet carries a hash of its content in the file name, and `next.config.ts` serves `/sprites/*` as `immutable`, so a file added there must have one too.
- `avatarLayers(look)` (`src/models/avatar/layers.ts`) resolves the layers of an `AvatarLook` sorted by `zPos`, and `CharacterAvatar` (`ui/custom/`) stacks them, animated by the `avatar-layer` utility in `globals.css`. `idle` loops and the others play once and hold their last frame (`loop` overrides it), so the caller switches back to `idle` on `onAnimationEnd`; a new `animation` starts from its first frame, and the same one plays again only with a new `key` on the component. `scale` is a whole multiple of the 64 px frame. Under `prefers-reduced-motion` it shows the first `idle` frame. Without `aria-label` it's hidden from assistive technology.
- `CharacterAvatar` with `still` shows only the first `idle` frame, as the class roster does, where many animated avatars would distract. An avatar that only illustrates (the landing page, `/creditos`) is `still` too: a looping `idle` next to text has no pause control (WCAG 2.2.2).
- LPC assets are CC-BY-SA, GPL or OGA-BY per piece and keep their license; the app code isn't affected. `/creditos`, linked from the Terms, lists every asset of the manifest with its authors, licenses and sources, so a new part is credited by importing it. The manifest is ignored by ESLint and cspell, since the credits come as upstream wrote them.

### Character

- A student plays one character per enrollment: the character class (`warrior`, `mage` or `healer`, one per outfit of the manifest, with the pt-BR names in `CHARACTER_CLASS_NAMES`, `src/models/character/constants.ts`), the appearance (body type, skin, hair style and color, outfit color) and `equippedItems`, all columns of `enrollments`. They're empty until the student chooses, and a check constraint keeps them all empty or all set (`hair_style` may be empty on a chosen character, which has no hair). The values aren't listed in the database, since an import can change the manifest: `characterModel` (`src/models/character/`) validates them, and only it writes them, except `equippedItems`, which `itemModel` writes (see Cosmetic items). A student who leaves and comes back keeps the character, since the enrollment is the same.
- The outfit colors belong to each character class (`outfitColorsOf`), so the schema rejects the color of another class on `outfitColor`. A radio value can't be null, so the form sends `NO_HAIR` (`'none'`) for a character without hair and the schema turns it into `null`; `lookFrom`/`appearanceOf` (`look.ts`) convert between the form values and an `AvatarLook`.
- `/aluno/turmas/[id]` asks for the character while it's empty (`characterModel.choose`, which only writes while `characterClass` is empty, so two submits never both go through) and after that lets the student change the appearance (`characterModel.updateAppearance`, which ignores a character class sent along and only writes while the class is the one the outfit color was checked against). A class the student never joined, one they left and an archived one all get `notFound()`.
- Only the teacher changes the character class after the choice, from the roster (`characterModel.changeCharacterClass`, "Trocar classe"): the outfit goes back to the first color of the new class, and the rest of the appearance stays, and so do the equipped items, except those exclusive to another class (`itemsExclusiveToOthers`), which leave the character but stay in the inventory. A student who hasn't chosen yet has no button.
- The roster shows each avatar `still`, a dashed frame and "Sem personagem" for a student who hasn't chosen (a pending one included), and the character class below the name.
- `FormRadioGroup` (`ui/custom/`) takes the hook's `control`, like `FormCheckbox`, and renders the 8bit `RadioGroup`, labelled by its `aria-labelledby`. The hook also returns `setValue`, which the form uses to move the outfit color to the new class when the student picks another one.

### Account deletion

- Every account can be deleted (#26) at `/professor/conta` or `/aluno/conta`, linked as "Minha conta" from `AppHeader`. The page renders `DeleteAccountSection` (`blocks/account/`, with its form and action, since both route groups use them), which says what goes with the account (`accountModel.deletionSummary`).
- `accountModel` (`src/models/account/`) deletes in one transaction of its own (`accountRepo`), not through Better Auth's `deleteUser`, which stays disabled: its hooks run outside the deletion. The foreign keys take the sessions, the sign-in methods, the classes of a teacher, the enrollments with their entries, requests and orders, and the inventory; the transaction also puts the unit of each pending reward order back in stock, deletes the rows of `verifications` whose `value` is the user id (invites, password resets) and the `verification_resends` of the email and the username. After the commit, the model publishes the three class events to every class that lost a student. It locks the enrollments in the order of their ids, as `ledgerRepo` does, so a purchase at the same time waits instead of deadlocking.
- An account with a password confirms with it (`auth.api.verifyPassword`, a wrong one is a field error); one without (Google only) needs a session younger than Better Auth's `freshAge` (24 hours), as Better Auth's own `deleteUser` does, and confirms in `ConfirmActionDialog`. The user is signed out and lands on `/entrar?conta=apagada`. No email is sent.
- Deleting a teacher deletes their classes, archived ones included, with every enrollment and entry in them; the students keep their accounts. A student the teacher invited who never accepted (no row in `accounts`) and who has no enrollment in another teacher's class goes too, since the account only holds what the teacher typed in.
- A teacher deletes a student's account from the roster ("Excluir conta", `accountModel.deleteInvitedStudent`) only when `users.createdById` is the teacher and every enrollment of the student, ended ones included, is in the teacher's classes, so nothing leaves another teacher's history. `listRoster` marks those students as `deletable`; any other gets `ValidationError`.

- Postgres with **Drizzle ORM** and the `pg` (node-postgres) driver, so the same code runs against the local container and Neon in preview/production. `drizzle-orm` and `drizzle-kit` are on the `1.0.0` release candidate (installed from the `@rc` tag, as the current Drizzle docs do): check the types in `node_modules/drizzle-orm` before reaching for a v0 API (e.g. `drizzle()` no longer takes `schema`, and the config has no `casing`).
- Infrastructure lives in `src/infra`: `compose.yml` declares the local services (Docker Compose, not `docker-compose.yml`): `database` (Postgres), `mail` (Mailpit, SMTP on `1025`, UI and API on `8025`) and `redis` (Redis, on `6379`, for the class events). `scripts/` holds the startup helpers and the sprite import, `database/` holds `client.ts`, `schema.ts` and the generated `migrations/`, `auth.ts` the Better Auth config, `email/` the mailer and templates and `realtime.ts` the Redis pub/sub. A piece stays a single file until it needs a second one; `scripts/` is a folder because its files run on their own. `drizzle.config.ts` stays at the root, where `drizzle-kit` looks for it.
- Tables are declared with `snakeCase.table(...)` from `drizzle-orm/pg-core`, so camelCase keys map to snake_case columns.
- Schema changes go through `pnpm migrations:generate --name <name>`, and the generated folder is committed. Don't edit a migration that was already applied; generate a new one.
- The seed scripts for manual testing live in `src/tests/seed/` (`seed.ts` for the full scenario, `users.ts`, `class.ts`, `awards.ts`, `reset.ts`), run with `tsx` (which resolves the `@/` alias) and `--env-file=.env.development`, and refuse any `DATABASE_URL` whose host isn't `localhost`. Accounts are inserted directly into `users` and `accounts`, since sign-up sends its email through `after()`, which only works inside a Next.js request. They all share `SEED_PASSWORD`, hashed by Better Auth (`auth.$context`); the pending student goes through `studentRepo.saveInvites` for the same reason. Everything else (classes, enrollments, characters, awards) goes through the models, so the ledger stays consistent. Each script appends what it created to `seed-credentials.md` at the root, git-ignored and ignored by ESLint; `db:reset` truncates every table of the `public` schema and removes the file. They live outside `src/infra/scripts/`, which can't import the models.
- `pnpm dev` is the startup script: `services:up` → `services:wait:database` → `migrations:up` → `next dev`. The compose services have no healthcheck because readiness is the wait script's job. Playwright's `webServer` (and so the pre-push hook and CI) goes through the same `pnpm dev`, so CI needs no service container.
- Local settings live in the committed `.env.development` (only local-only values: the containers' credentials and URLs, plus a `BETTER_AUTH_SECRET` that no hosted environment uses; never a hosted secret). There is no `.env`/`.env.example`. The compose services read it through `env_file`, so the `POSTGRES_*` values are declared once there; `DATABASE_URL` repeats them literally (`process.loadEnvFile` doesn't expand variables), so keep both in sync. `drizzle.config.ts` and the wait script load `.env.development` only when `DATABASE_URL` isn't already set, so hosted environments keep their injected value. `drizzle.config.ts` prefers `DATABASE_URL_UNPOOLED` (Neon's direct connection) over the pooled `DATABASE_URL`.

Don't `vercel env pull` the Neon variables into it: `.env.local` takes precedence over `.env.development`, so `next dev` would hit Neon. The Neon integration is connected to Production and Preview only, not Development.

### Forms

- Forms use **React Hook Form** (`react-hook-form`, with `@hookform/resolvers`) and uncontrolled inputs for client-side validation, with the model's **Zod** schema, and call **Server Actions** with the typed values. They need JavaScript. Stay on `react-hook-form` v7: its docs only declare React Compiler support for v8, still in beta, so the forms' e2e tests are what covers the compiler (Vitest runs without it).
- A form lives in the route's `_components/`: `action.ts` (`'use server'`) and `<name>-form.tsx` (`'use client'`). The schema comes from `src/models/<domain>/schema.ts`. It only declares rules and messages for Zod, so it has no unit test of its own: the forms' e2e tests cover what the user sees.
- `action.ts` receives the typed input, wraps the model call in `formAction(input, async (values) => ...)` (`src/entry/form-action.ts`) and returns `formSuccess(message)` or calls `redirect()`. The wrapper turns whatever the model throws into the `FormState` the form renders:
  - a `ZodError` becomes `errors` (the first message per field, a nested field under its dotted path, e.g. `links.0.url`);
  - an `AppError` becomes `message` + `action` for the whole form. A business rule that belongs to one field is thrown as a `ZodError` with that `path`;
  - anything else is logged and shown as a generic message, so the user never sees an error boundary for a failed submit;
  - `redirect()`/`notFound()` are rethrown (`unstable_rethrow`).

  It also gives every result a unique `id`, so a repeated identical error still updates the UI.

- The client form calls `useFormAction({ schema, defaultValues, action })` (`src/app/hooks/use-form-action.ts`) and renders `<form {...formProps}>`, a `<FormField label=... {...field('name')} />` per field (`name` is typed by the schema's fields), `<FormMessage state={state} announcement={announcement} />` and `<SubmitButton pending={pending}>`. `FormCard` (adapted from 8bitcn's `login-form` block), `FormField`, `FormCheckbox` (takes the hook's `control`), `FieldFrame`, `FormMessage` and `SubmitButton` live in `src/app/components/ui/custom/`. A list with a button per row that isn't a form of fields (e.g. "Desativar", "Usar poder") uses `ActionButton` there, which hands the result to the list so one `FormMessage` serves every row. `FieldFrame` holds the label, hint and error of a field and hands the ids and ARIA attributes to its child, so a control other than the text input of `FormField` goes inside it. Pages build notices (e.g. from `?error=`) with `formError(...)`/`formSuccess(...)` and pass them as `initialState`.
- `GoogleSignInForm` has no fields, so it stays on `useActionState` with the same `formAction`, `FormMessage` and `SubmitButton`.
- How it behaves, so don't "simplify" it away:
  - The `<form>` keeps `method="post"`, so a click before hydration never puts a password in the URL. `onSubmit` validates on the client and calls the action inside `startTransition`, the only way `redirect()` reaches the `RedirectBoundary`; nothing resets the form.
  - Field errors live only in React Hook Form. With `mode: 'onTouched'` a field shows its error once it was left or the form was submitted, and revalidates on every change after that. Server field errors arrive through `setError`, and each one hides once its field is edited.
  - React Hook Form validates one field at a time, so a field another one depends on is declared with `field('password', { revalidates: 'passwordConfirmation' })` (or a list of fields). It only revalidates a field already visited or invalid; `deps` would reveal an error on a field not visited yet.
  - `SubmitButton` prevents the default of `mousedown`, so the focus stays on the field: the blur would reveal its error and move the button under the pointer, losing the click. Don't replace it with a check of the blur's `relatedTarget`: Safari doesn't focus a button on click. `FormCard` does the same for the links inside it.
  - After a failed submit (client or server) React Hook Form moves the focus to the first invalid field, before the commit that adds its `aria-invalid` and error description. That loss is accepted, since `FormMessage` reads out the first field error (`announcement`). The announcement also covers a field that already has the focus, where moving the focus announces nothing. A client-side rejection clears the previous answer of the Server Action. A visible form message (success, an `AppError`, or one rendered with the page such as an expired link) takes the focus. `FormMessage` is a live region that stays mounted (`sr-only` while empty); `SubmitButton` uses `focusableWhenDisabled` so focus survives the pending state; that sets `aria-disabled` instead of `disabled`, so it styles the `aria-disabled:` state itself, shows the 8bit `Spinner` while pending and announces the pending state in its own live region, since not every screen reader voices `aria-disabled` on the focused button. `FormMessage` turns the live region `sr-only` whenever there's no visible message, not with `empty:sr-only`, since the announcement alone would add a gap to the form.
  - A `type="date"` typed only in part reports a blank value, which the schema would take as no date, so `useFormAction` wraps the resolver (`withIncompleteDates`) and gives that field its own error (`validity.badInput`).
  - `FieldFrame` builds its ids with `useId`, so two forms on a page never share an `id`. In e2e tests, check a field error with `toHaveAccessibleDescription` on the field rather than `getByText`, which also matches the announcement.

### Auth & email

- **Better Auth** (`src/infra/auth.ts`) with `drizzleAdapter` from `@better-auth/drizzle-adapter/relations-v2` (the plain export targets Drizzle v0), `usePlural` and `generateId: 'uuid'`. Its tables live in `src/infra/database/schema.ts`, hand-written in the `snakeCase.table` style: when a Better Auth plugin or option adds fields, run `pnpm dlx auth@latest generate --config src/infra/auth.ts --output <scratch file>`, port the diff by hand and generate a migration. Never point `--output` at `schema.ts`.
- `role` (`teacher` | `student`) is an `additionalField` with `input: false` and `defaultValue: 'teacher'`: Better Auth rejects it from any request body, even server-side calls, so the role of a new account comes only from the server flow that creates it. The model wraps every sign-up in `withSignUpRole(role, ...)` (an `AsyncLocalStorage` in `src/infra/auth.ts`) and `databaseHooks.user.create.before` applies it; for Google, a `before` hook on `/sign-in/social` copies it into the OAuth state with `addOAuthServerContext`, which the callback request reads back with `getOAuthState()`. A request straight to `/api/auth/sign-up/email` has no role and gets a `403`, since it would skip the terms acceptance. Never read the role from `additionalData` or the request body.
- The terms live at `/termos` and `/privacidade` (`(pages)/(legal)/`, with the controller's name, the contact email and the update date in `legal-info.ts`). Every sign-up records `termsAcceptedAt` (`input: false`) together with the role in `databaseHooks.user.create.before`, so a new flow that calls `withSignUpRole` must collect the acceptance first. The email forms require the `acceptedTerms` checkbox and the model rejects a sign-up without it; on Google the sign-up page shows `GoogleTermsNotice` next to the button. Accounts older than #7 keep `termsAcceptedAt` empty.
- `/cadastro` is the role choice; `/cadastro/professor` and `/cadastro/aluno` are the sign-up pages. Every account has a valid email, verified before its first sign-in, students included; students also have a `username` (Better Auth `username` plugin, rules in `src/constants/user.ts`, stored in lowercase). `/entrar` serves both roles with a single "E-mail ou usuário" field: a value with `@` signs in by email, any other by username, and every credential failure shows the same copy.
- `baseURL` is dynamic (`allowedHosts`), so each Preview URL works without `BETTER_AUTH_URL`. Only this project's hosts are listed; never add `*.vercel.app`, which would trust any Vercel deployment.
- Google sign-in (`socialProviders.google`) is enabled only when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set; pages check `isGoogleSignInEnabled` and hide "Continuar com o Google" without them, so tests and CI never need the credentials. `disableImplicitSignUp` keeps Google from creating an account on `/entrar`: only a sign-up page passes a `signUpRole` (which turns on `requestSignUp`), so the user always picks the role. `mapProfileToUser` drops the Google picture, so a Google account keeps only what the sign-up form would collect (name and email). Account linking is Better Auth's default for every role (Google links only when both sides verified the same email). The callback's `?error=` lands on the page with `?origem=google` and is shown by the Google form itself (`googleNoticeFrom` in `(pages)/(auth)/google-notice.ts`), so a new attempt replaces it; on each sign-up page the Google form is a child of the sign-up form, which hides it after an email sign-up, since Google can't link to the still unverified account. On Vercel, `oAuthProxy` sends Previews through the production callback (`OAUTH_PROXY_SECRET`, the same in Production and Preview), since Google doesn't accept wildcard redirect URIs; locally Google uses its own `localhost` redirect URI, so the plugin is off and the proxy secret never leaves Vercel. The Google Cloud setup is in `README.md` (#44).
- `src/models/authentication/` wraps `auth.api.*` (sign-up, sign-in, password reset): the auth pages' actions call it with `headers: await headers()` (the dynamic `baseURL` and rate limiting need the request host/IP), and `nextCookies()` stays the last plugin so those actions can set cookies. Its `errors.ts` maps the Better Auth error codes we expect to `UnauthorizedError`/`ValidationError` copy; a code without copy stays an unexpected error. Pages read the session with `getSession()` from `src/entry/session.ts`. `src/app/api/auth/[...all]/route.ts` serves the links sent by email (verification, password reset).
- Teachers land on `/professor` and students on `/aluno` (`DASHBOARD_PATHS` in `src/constants/user.ts`), and `/` is the landing page for a signed-out visitor (`(pages)/page.tsx`, with its sections in `(pages)/_components/`) and redirects a signed-in user to the dashboard of their role. A page of a role area calls `requireRole(role)` from `src/entry/session.ts`, and so does its layout, which also needs the user: a layout doesn't re-run on client navigation nor stop the page below it from rendering, so the check in the layout alone isn't enough. `requireRole` sends a signed-out user to `/entrar` and a user of another role to their own dashboard. There is no `proxy.ts`: the role lives in the database and the proxy also runs on prefetches, so it could only read the cookie. A Server Action of a role area makes the same check, since it can be called without going through the page.
- The verification link is resent from the sign-up success message and from the "Confirme seu e-mail antes de entrar." error on `/entrar` (`ResendVerificationButton`, `(pages)/(auth)/_components/`), with a cooldown of `VERIFICATION_RESEND_COOLDOWN_SECONDS` (`src/models/authentication/constants.ts`). Better Auth's rate limit doesn't cover it: it skips calls made through `auth.api` and counts per IP. The cooldown lives in `verification_resends`, keyed by the email or username the user typed (trimmed, in lowercase), not by the account, so an email without an account gets the same answer; sign-up and a sign-in rejected for an unverified email also start it, since Better Auth just sent a link. `resendVerificationEmail` waits at least 500 ms, Better Auth's floor for that send, so a pending student's invite doesn't answer faster. The countdown stays out of the button's accessible name and only its start and end are announced.
- Emails are sent with `nodemailer` over SMTP (`src/infra/email/mailer.ts`): Resend's SMTP (`smtp.resend.com`, the API key as password, sending as `nao-responda@` the integration's `RESEND_EMAIL_DOMAIN`) when `RESEND_API_KEY` is set, else `SMTP_URL` (Mailpit). The transporter is created per send, so importing the module never needs the variables (`next build`, the Better Auth CLI). Auth emails are scheduled with `after()` so their timing doesn't reveal whether an account exists. `scheduleEmails` does the same for a list, one at a time, and a failed address doesn't stop the others. Links in these emails take their host from `appBaseURL(headers)` (`src/infra/auth.ts`), which applies `allowedHosts`, never directly from the `Host` header.
- The Resend integration (domain `inovaclass.diasjoaovitor.com.br`, region `sa-east-1`) is connected to Production and Preview only (`vercel integration add resend/resend-email -e production -e preview --no-env-pull`): pulling `RESEND_API_KEY` into `.env.local` would make local runs send real email.
- Tests read emails from Mailpit through `orchestrator.waitForLinkSentTo(email)` (`src/tests/orchestrator.ts`).

### Testing

- Unit tests: **Vitest** (`vitest.config.mts`, project `unit`), `jsdom` environment, native Vite `resolve.tsconfigPaths` (no `vite-tsconfig-paths` plugin needed). Picks up `src/**/*.test.{ts,tsx}` outside `src/tests`, next to the code they test. Component tests use `@testing-library/react` / `@testing-library/dom`. `vitest.setup.ts` (`setupFiles`) runs Testing Library's `cleanup` after every test, so test files don't repeat `afterEach(cleanup)`.
- Integration tests: Vitest project `integration` (`node` environment, files run one at a time), in `src/tests/integration/`, mirroring the layer they test (e.g. `models/authentication.test.ts`). They call models against the local Postgres, Mailpit and Redis, so `pnpm test:integration` starts the services and migrates first. `src/tests/integration/setup.ts` loads `.env.development` and replaces `after()` from `next/server`, which only works inside a Next.js request, with a plain call. Shared test helpers (`newUser()`, `newStudent()`, `newClass()`, `newEmail()`, `newUsername()`, `newPassword()`, reading Mailpit) live in `src/tests/orchestrator.ts`, used by integration and e2e tests alike. Use unique data per test instead of clearing the database: test data comes from `@faker-js/faker` (`fakerPT_BR`) through the orchestrator, except emails and usernames, which carry a UUID so they never repeat, and literal values that are the point of the test (e.g. an invalid email).
- E2E tests: **Playwright** (`playwright.config.ts`), tests live in `src/tests/e2e`, single `chromium` project, `webServer` auto-starts `pnpm dev` against `http://localhost:3000`. Failure artifacts go to `test-results/` (git- and ESLint-ignored). Assertions wait up to 15s (`expect.timeout`) and a test up to 60s (`timeout`), since `pnpm dev` compiles each route on its first request; don't lower them to the defaults of 5s and 30s. Local runs use 3 workers (`workers`), since more compile too many routes at once on a cold `.next`. There are no global retries: a known flaky test gets `test.describe.configure({ retries })` in its own `describe`, with a comment linking the issue that tracks it.
- Only test logic we wrote (filtering, lookups, mappings, transforms, a model's rules and error mapping). Don't test library or framework behavior (e.g. a component that only passes props or HTML through, a Zod schema's `trim`/`min`/`max` and the messages we hand it, `Link` routing), and drop a test whose main cost is a mock needed only to render. Prefer a unit test; add an e2e test only for what a unit test can't cover.
- Older issues may ask for tests that break the rule above. Skip them without asking, and list them as dropped in the closing comment.
- Scripts: `pnpm test` (unit, run once) / `pnpm test:watch` (unit, watch mode) / `pnpm test:integration` (services + migrations + integration) / `pnpm test:e2e` (e2e) / `pnpm test:e2e:ui` (e2e, Playwright UI mode). `lint-staged` runs `vitest related --project unit`, so commits never need the services.
- CI (`.github/workflows/ci.yml`, triggered on `pull_request`) runs, in order: `commitlint` over the PR's commit range, `pnpm type-check`, `pnpm eslint:check`, `pnpm prettier:check`, `pnpm spell:check`, `pnpm test`, `pnpm test:integration`, then installs Chromium (`pnpm exec playwright install --with-deps chromium`) and runs `pnpm test:e2e`.

Read its source from the registry (`https://8bitcn.com/r/<block>.json`, the `content` of each file), never install it with the CLI, and port it like an 8bit component: onto our `ui/8bit/` and `ui/shadcn/` components (port any missing 8bit component first), Base UI, `cn`, arrow functions and pt-BR copy, with a credit comment linking the block's docs page. Prefer the shadcn tokens (`bg-background`, `text-muted-foreground`, `border-border`, ...) for surfaces and text, so both themes stay consistent. Where CSS variables can't be read (a canvas, `ImageResponse`), copy the palette value and name it in a comment.

## Development Workflow

The end-to-end flow (planning, issues, branches, commits, pull requests and closing) is described in [`docs/development-workflow.md`](./docs/development-workflow.md). Follow it for any issue.

## Branch Rules

Work for an issue is committed on a new branch, never directly on `main`. Branch names follow `<scope>/<title>#<issue>`, or `<scope>(<target>)/<title>#<issue>` when the work is very specific:

- `<scope>` is one of the semantic prefixes from the Commit Rules below, without the emoji (`feat`, `fix`, `docs`, `chore`, ...).
- `(<target>)` is optional: the page, component or other specific area the work touches (e.g. `home`, `card`).
- `<title>` is a short, lowercase, hyphen-separated summary in English.
- `#<issue>` is the number of the associated issue.

Examples: `feat/home-page#3`, `fix(card)/focus-ring#7`. Parentheses and `#` are special characters in shells, so quote the branch name in commands (e.g. `git switch -c 'fix(card)/focus-ring#7'`).

## Issue Rules

Before closing an issue, tick every completed checklist item (`- [x]`) in its body, e.g. with `gh issue edit <number> --body-file <file>`. Don't close an issue that still has unchecked items unless they were dropped or moved, and say so in the closing comment.

## Documentation Rules

`AGENTS.md` and `README.md` record only project conventions: what to do, where things live and how to handle a given case. Answers to the user's one-off questions (e.g. "why don't we use X?") stay in the conversation and are not written into them. Keep a "why" only when it prevents a likely mistaken "fix". If a change touches a convention, update both files in the same branch.

[`docs/local-testing.md`](./docs/local-testing.md) is the step-by-step guide to trying every feature by hand. A change to what a user sees or does (a new flow, a renamed label, a removed page) updates it in the same branch.

## Task Rules

Never start working on a task on your own, even when asked to move on to the next one or in auto/agentic mode. First present a summary of the plan (the issue, branch name, steps, files touched and any open decisions) and wait for explicit approval before creating the branch, installing dependencies or editing code. Read-only investigation (issues, docs, code) needs no approval.

## Commit Rules

Never run `git commit` on your own, even in auto/agentic mode. Only propose a commit message when the user asks for one, and create the commit only after explicit approval of that message.

Commit messages must be in English and follow this format:

- Use the following semantic prefixes: `🎉 init, ✨ feat, 🐛 fix, 📚 docs, 💎 style, 📦 refactor, 🚀 perf, 🚨 test, 🛠 build, ⚙️ ci, ♻️ chore, 🗑 revert`
- The message must be in the imperative mood and in lowercase.
- Write the commit body.
- Reference an associated issue by number, if it exists, using the format `Issue: #<number>`.

Example:

```text
✨ feat: add product page

Add the new product page for the product listing with the following features:
- Create a new product
- Update a product
- Delete a product

Issue: #1
```
